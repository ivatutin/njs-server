# Контракт Auth v1 — заморозка (v1.4, 16.10.2026)

## Принцип

Контракт — **единственная общая точка** фронта и бэка. Пока он не меняется, обе рабочие сессии независимы.

**Источник истины (спецификации живут в репозиториях, здесь — только маркер версии):**
- `vue-app-base/docs/integration-backend.md` § «Auth endpoints planned» — эндпоинты и DTO.
- `njs-server/docs/auth-suite-backend-checklist.md` — backend-обязанности.
- `vue-app-base/src/shared/api/error-codes.ts` — реестр кодов ошибок.

## Что заморожено (v1.4)

- **Пути и методы** эндпоинтов Phase 0–4.
- **Формы запроса/ответа (DTO)** — как в спецификациях.
- **Коды ошибок** (поле `error` в теле ответа) — совпадают с реестром фронта. Это главная точка сцепления.
- **Семантика anti-enumeration:** `sign-in`-purpose OTP, `forgot-password`, `verify-email/resend` → **всегда** 200/202.
- **Каналы подтверждения телефона (v1.2):** SMS-код (`POST /auth/otp/send` + `POST /auth/otp/verify`) и
  обратный звонок (`POST /auth/phone/call` + `GET /auth/phone/call/:challengeId`) — оба выдают
  **один и тот же** `verificationToken`, который затем предъявляется в существующие
  `POST /auth/sign-up/phone` / `POST /auth/sign-in/phone` без изменений.
- **Социальный вход (v1.3):** `GET /auth/providers`, `POST /auth/oidc/callback`,
  `POST /auth/providers/:id/callback` (`:id = 'telegram-widget'`; `telegram-bot` / `vkid` / `yandex` —
  **зарезервированы**, добавляются аддитивно отдельными предложениями).
- **Политика линковки (v1.3):** автоматическая привязка провайдера к существующему аккаунту по совпавшему
  контакту **запрещена** → `409 ProviderAccountLinked` (identity уже привязана) либо `409 ContactAlreadyExists`
  (контакт занят другим аккаунтом). Пользователь входит прежним способом; своего эндпоинта привязки в v1.3 нет.
- **Неполный социальный профиль (v1.3):** пользователь получает обычные токены + `needsContactCompletion: true`,
  но **статус аккаунта = `pending_verification`** — дальше работает существующая машина состояний фронта
  (`/system/account-status`). Новые scopes **не вводятся**.
- **`state` / PKCE (v1.3):** `codeVerifier` и `state` — **клиентские**; фронт обязан сверить `state` со своим
  сохранённым значением **до** вызова `POST /auth/oidc/callback`. Доказательство для бэкенда — сам успешный обмен `code`.
- **Выход со всех устройств (v1.4):** `POST /users/me/logout-all` (protected, **без тела**) → `204`.
  Гасит **все** сессии Keycloak (refresh-токены всех устройств) **и** ставит метку отзыва по `sub` — все выданные
  access-токены, **включая текущий**, перестают приниматься (`401`). **Без `X-Reauth-Token`** (операция не даёт
  захвата аккаунта и иначе недоступна passwordless-пользователям). Идемпотентно; отказ инфраструктуры → `503`
  без нового кода. Тело ответа **пустое** (провайдер не сообщает число погашенных сессий). `POST /auth/sign-out`
  не меняется.

## Реестр кодов ошибок (сцепление фронт ↔ бэк)

| Код | Когда |
|---|---|
| `InvalidCredentials` | неверные креды / неизвестный телефон при sign-in (единый ответ) |
| `ContactAlreadyExists` | регистрация занятого email/phone |
| `ContactNotFound` · `ContactAlreadyVerified` | операции с контактами |
| `PasswordPolicyViolation` | политика Keycloak (+ `details.message`) |
| `TermsNotAccepted` | `acceptedTerms !== true` |
| `OtpInvalid` · `OtpExpired` · `OtpTooManyAttempts` · `OtpRateLimited` | OTP send/verify |
| `VerificationTokenInvalid` · `VerificationTokenExpired` | phone sign-up/sign-in |
| `ReauthTokenInvalid` · `ReauthTokenExpired` | защищённые операции |
| `ChangeTokenExpired` · `ContactChangeAlreadyPending` | смена контактов |
| `InvalidToken` ⟵ *v1.1* | невалидный / просроченный / отозванный access или refresh (401) |
| `InvalidContacts` ⟵ *v1.1* | нарушен инвариант контактов: нет ни email, ни phone; прямая смена verified-контакта (422) |
| `UserNotFound` ⟵ *v1.1* | пользователь не найден (404; в основном админские операции) |
| `SocialAuthFailed` ⟵ *v1.3* | доказательство провайдера не прошло: просроченный `auth_date`, битая подпись, отказ обмена `code` (422) |
| `ProviderAccountLinked` ⟵ *v1.3* | federated identity уже привязана к другому нашему аккаунту (409) |

> Коды, помеченные *v1.1*, уже реализованы в бэкенде, но отсутствовали в реестре фронта — добавлены аддитивно.

> **v1.2 новых кодов не добавляет.** Терминальные состояния звонкового канала (`expired`, `failed`) отдаются
> как поле `status` при HTTP 200 — это состояние ресурса, а не ошибка клиента (см. changelog и решение).

> Точный перечень и формулировки — в `error-codes.ts`; при расхождении истина там.

## Что НЕ входит в контракт (свобода реализации)

- Внутреннее устройство: Redis-ключи, argon2id, структура NestJS-модулей, вызовы Keycloak Admin.
- Хранение токенов на фронте, способ рендеринга страниц.
- Версии библиотек и инфраструктуры (Node, Keycloak, Redis).

## Протокол расширения контракта ошибок

### Классификация изменения

| Тип | Пример | Ломает ли фронт | Версия |
|---|---|---|---|
| **Аддитивное** | новый код, которого раньше не было | Нет — клиент на неизвестный код показывает generic | `v1.x → v1.(x+1)` |
| **Семантическое** | существующий код меняет смысл или HTTP-статус | Да | согласованно |
| **Переименование / удаление** | `Xxx` → `Yyy` | Да | deprecation-окно |

### Инвариант, делающий аддитивные изменения безопасными

Клиент **никогда не ломается на неизвестном коде**: `matchError` → `false`, `getErrorMessage` → «Что-то пошло не так».
Это поведение зафиксировано в `error-codes.ts` и обязательно к сохранению. Благодаря ему новый код можно
выкатить на бэке **до** обновления фронта — сессии не блокируют друг друга.

### Правила добавления нового кода

1. Имя: PascalCase, без суффикса `Error`, схема `<Домен><Условие>` (`CallChallengeExpired`).
2. Один код = один HTTP-статус; если есть `details` — описать форму (пример: `OtpRateLimited` → `details.retryAfter`).
3. Код добавляется **в оба зеркальных реестра**: `njs-server/src/shared/domain/errors/error-code.ts`
   и `vue-app-base/src/shared/api/error-codes.ts` (+ `ERROR_MESSAGES`).
4. Обновляются этот файл и его changelog.

### Кто и как

1. Рабочая сессия **останавливается** и запрашивает изменение (сама реестр не правит).
2. Координатор: правит этот файл → версия `vN.(M+1)` + changelog → выдаёт задачу на обновление реестров обеим сторонам.
3. Обе сессии возобновляются с новой версией.

### Гардрейлы против тихого расхождения (drift)

- **Backend:** тест — каждый наследник `DomainError` даёт непустой `code`; список кодов зафиксирован снапшотом.
- **Frontend:** `ERROR_MESSAGES: Record<ErrorCode, string>` — компилятор требует сообщение на каждый код (уже есть).
- **Координатор:** при наблюдении сверять два реестра; расхождение → запись в [../status.md](status.md).
