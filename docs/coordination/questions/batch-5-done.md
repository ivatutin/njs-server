## 1. Дефект «пустой профиль → 400 → 503»: что нашёл

### 1.1. Политика реалма (это и есть «причина в Keycloak»)

```
GET /admin/realms/{realm}/users/profile →
  firstName: required = { "roles": ["user"] }
  lastName:  required = { "roles": ["user"] }
  unmanagedAttributePolicy: ENABLED
```

Следствия, проверенные живьём:

- аккаунт **с ролью `user`** и пустыми `firstName/lastName` **не может войти вообще** — password grant отвечает
  «account not fully set up», наш API отдаёт `401 InvalidCredentials` (анти-энумерация);
- обнулить обязательное имя у роли `user` через Admin API **нельзя молча**: `PUT` с `lastName: ""` отвечает `204`,
  но значение **не меняется** (Keycloak игнорирует очистку обязательного атрибута);
- имя валидируется `person-name-prohibited-characters`, но кириллица, цифры, дефис, пробел и апостроф проходят (`204`).

**Вывод:** состояние «роль `user` + пустые имена» достижимо только *до* выдачи роли (назначение роли профиль не
валидирует). Значит на приёмке фронта это был **дрейф**: токен выдан раньше, а имена к моменту `PATCH` оказались
пустыми — ровно тот класс сбоя, который у нас уже описан в `updateContacts` (там старый `PUT` однажды снёс
`firstName/lastName/email`).

### 1.2. Что воспроизвести не удалось (и почему)

Точное тело того `400` получить не смог: Keycloak перезапускался 20.10 в 13:41, admin-events и логи того запроса
истекли. Смоделировал 8 состояний и прогнал `PUT` тем же представлением, что строит адаптер, — **все `204`**:

| Состояние пользователя | `PUT` |
|---|---|
| без имён, без роли | 204 |
| без имён + роль `user` | 204 |
| `lastName: null` / `""` / ключа нет | 204 / 204 / 204 |
| имена кириллицей / с цифрой / дефисом / пробелом / апострофом | 204 |
| `username` = email (как у `user-dev`) | 204 |
| `requiredActions: ["VERIFY_EMAIL"]`, `emailVerified: false` | 204 |
| пустые `attributes`, phone-пользователь без email | 204 / 204 |

Поэтому в отчёте не утверждаю, что знаю точный код ошибки Keycloak. **Что теперь будет:** если это повторится,
в логе появится `[status 400] body={"error":"…"}` — и кейс станет разбираемым.

### 1.3. Что починил

1. **Убрал `null` из тела `PUT`.** Единственное системное отличие нашего запроса от ручного, который прошёл (`204`):
   в полях имени мы отправляли `null`, когда в Keycloak имени не было. Теперь всегда строка: `undefined` → текущее
   значение, `null` → `''`. Для KC это валидное «пусто», и семантика контракта («`null` в запросе = очистить»)
   сохраняется. Комментарий в адаптере фиксирует политику реалма, чтобы кейс не «переоткрывали».
2. **Логирование тела ответа Keycloak** (п. 2 задачи). Было: `Request failed with status code 400`. Стало:
   `profile update: keycloak write failed kc=… fields=[firstName=set] currentName=[first=empty,last=empty]:
   Request failed with status code 400 [status 400] body={"error":"error-user-attribute-required", …}`.
   Без PII: только имена полей (`set`/`clear`), состояние «пусто/задано», статус и тело ошибки (обрезано 400 симв.).
3. Тесты: +2 в `keycloak-identity-profile.adapter.spec.ts` — «пустой профиль: второе имя уходит `''`, в JSON нет
   `null`» и «тело Keycloak попадает в лог, значения имён — нет».

### 1.4. Живая проверка после фикса (host-инстанс, 3101)

```
sign-in (имена есть)                       -> 200
PATCH {firstName:null,lastName:null}       -> 200; KC: first=[], last=[]        (очистка работает)
PATCH {firstName:'Petr'} на пустом профиле -> 200; KC: first=[Petr], last=[]
GET /users/me                              -> first=Petr, last=
создание пользователя с ролью user и пустыми именами -> sign-in 401 (по политике реалма)
```
