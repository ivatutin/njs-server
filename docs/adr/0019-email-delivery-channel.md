# ADR 0019: Канал доставки email (OTP-коды при смене контакта)

- **Дата:** 2026-10-15
- **Статус:** **Accepted** (решение координатора, вариант E1 с провайдером DashaMail). Реализовано: порт `EMAIL_SENDER`,
  dev-реализация `ConsoleEmailSender`, боевой адаптер `DashaMailEmailSender`, конфиг и fail-closed.
- **Связано:** ADR-0017 (смена контакта, `channel: 'email'`), ADR-0011 (OTP-хранилище), ADR-0014 (звонковый канал —
  образец fail-closed dev-провайдера), контракт v1.3

## Контекст

`POST /users/me/contact-change/request` принимает `channel: 'email'`, то есть **код должен уйти на новый email**.
При этом в проекте не было ни одного email-отправителя: писем из приложения не существовало, всю почту отправлял сам
Keycloak (verify-email → Mailpit в dev, SMTP реалма в проде). Абстракции были только для SMS (`SmsSender`) и звонка
(`PhoneCallProvider`), то есть email-ветку трио нечем было обслужить. Находка зафиксирована вопросом координатору
(`docs/handoff/njs-server-question-email-otp.md`) — он выбрал **E1** и назвал провайдера.

## Решение

**Свой канал доставки.** Порт `EMAIL_SENDER` рядом с `SmsSender`:

- **dev/CI** — `ConsoleEmailSender`: код печатается в лог (как `ConsoleSmsSender`) → фронт разблокирован сразу;
- **prod** — `DashaMailEmailSender`: `POST https://api.dashamail.com/v2/transactional/messages`,
  `Authorization: Bearer <API_KEY>`;
- **без сконфигурированного провайдера** `channel: 'email'` → `503` (fail-closed; поведение повторяет
  `ConsolePhoneCallProvider`, который в `NODE_ENV=production` отказывает).

Контракт не меняется: код по-прежнему приходит в `newCode`, `newChallengeId` остаётся.

### Требования к реализации (из решения координатора)

1. **Свой `message_id`** в запросе — корреляция с записью `contact-change` и идемпотентность на стороне провайдера.
   Чужие `transaction_id` не храним.
2. **Заголовок `X-Dashamail-Unsub-Ignore: 1`** — обязателен. Иначе адрес, который «отписался или пожаловался», тихо
   не получит письмо: запрос выглядит успешным, письмо получает `Bounced` (код 673) и событие `dropped`.
   OTP — служебное письмо, человек обязан его получить.
3. **Доставка асинхронная.** POST сразу возвращает id, письмо уходит в очередь → `request` не ждёт доставки и не
   гейтит по ней; UX строится на «код отправлен, может прийти через секунды» + перевыпуск.
4. **Домен отправителя обязателен.** `from_email` — на домене, добавленном и подтверждённом (DKIM + SPF), иначе письма
   не уйдут, а журнал/статистика вернут `code 34`. Это прод-шаг → `DEPLOYMENT.md §7`, рядом с SMTP реалма.
5. **Webhooks на `Bounced` / `dropped`.** Включить минимум на эти два события, чтобы поддержка видела «письмо не дошло»
   (битый адрес, переполненный ящик). Хранить последний статус **по своему** `message_id`; адрес в логи не писать.
6. **Keycloak тоже отправляет письма** (verify-email, сброс пароля, Review Profile) — у него свой SMTP. У DashaMail есть
   SMTP API: проверить и направить realm SMTP туда → один провайдер, один DKIM-домен, один прод-пункт вместо двух.
7. **Комплаенс (в плюс):** DashaMail — ФЗ-152, данные в РФ, в реестре отечественного ПО. Адреса пользователей уходят
   третьей стороне → отметка в списке обработчиков ПДн.

### Почему не E2 и не E3

- **E2** (делегировать email-OTP в Keycloak ссылкой): ломает замороженный контракт (`verify` по ссылке вместо `newCode`),
  даёт два разных UX на одну операцию (телефон — код, email — ссылка) и требует сначала записать новый адрес
  пользователю — конфликт с инвариантом «verified-контакт напрямую не меняется». Отклонено.
- **E3** (сузить трио до телефона): продуктовая дырка — email сменить нельзя, плюс правка enum в контракте. Отклонено.

## Перевыпуск кода — штатный путь

По контракту повторный `request` при активном change → `409 ContactChangeAlreadyPending`, значит штатный путь для
фронта — **`cancel` → `request`** (новый change, новые челленджи, новый `changeToken`).

Дополнительно `OTP_CHALLENGES.verify` проверяет код по паре `(target, purpose)`, поэтому технический перевыпуск
челленджа на том же контакте не ломает уже начатый change (внутренняя устойчивость к гонке, а не пользовательский путь).
Cooldown 60 с на target (`OtpRateLimited` с `retryAfterSeconds`) фронт показывает отсчётом.

**Для фронта:** шаг «отменить и начать заново» при не полученном коде должен быть **явным в UI** — иначе пользователь
застревает на экране ввода кода (повторный `request` вернёт `409`).

## Последствия

- Новые переменные окружения: `DASHAMAIL_API_KEY`, `DASHAMAIL_FROM_EMAIL`, `DASHAMAIL_FROM_NAME`, `DASHAMAIL_API_BASE_URL`
  (пусто → dev-лог; в production email-ветка отвечает `503`).
- Код: `src/modules/otp/domain/ports/email-sender.port.ts`, `infrastructure/email/{console,dashamail}-email.sender.ts`,
  конфиг `src/config/dashamail.config.ts`, маска адреса `maskEmail` в `domain/target-mask.ts`.
- Тесты: `test/infrastructure/{dashamail,console}-email.sender.spec.ts` — свой `message_id`, `X-Dashamail-Unsub-Ignore`,
  ретраи 5xx (3 попытки), отсутствие ретрая на 4xx, маппинг `code 34/673`, fail-closed в проде.
- **Прод-пункты (чек-лист):** подтверждённый домен DKIM/SPF, API-ключ, webhook `Bounced`/`dropped`,
  realm SMTP Keycloak → DashaMail; сверить поля тела запроса с актуальной документацией при выдаче ключа
  (из нашей сети док недоступна: `401/404`).
