# ADR 0017: Смена контакта (email/phone) — синхронизация Keycloak и shadow-БД

- **Дата:** 2026-10-15 (ред. 2 — после ревью координатора)
- **Статус:** **Accepted и реализовано** (ред. 3 — после реализации и живой приёмки 16.10.2026). Все срезы в `main`:
  доменный метод `User.applyVerifiedContactChange`, shared-порты `OTP_CHALLENGES` / `USER_CONTACTS` / `CONTACT_CHANGE_NOTIFIER`,
  `changeToken`-стор, use-case'ы `request`/`verify`/`cancel`, HTTP-слой; приёмка — в
  `docs/auth-suite-backend-checklist.md` (§ «Phase 4 — трио contact-change»).
  **Приёмка нашла и закрыла два дефекта:** (1) повторный `request` при активной смене отвечал `OtpRateLimited`
  вместо `ContactChangeAlreadyPending` — теперь слот проверяется до лимитов; (2) `PUT /users/{id}` в Keycloak —
  полная замена представления, из-за чего смена одного контакта затирала `email`/`firstName`/`lastName` и ломала
  вход (`Account is not fully set up`) — теперь read-modify-write.
- **Обновление 16.10.2026 (ред. 4): правило починки флагов подтверждения.** По ревью координатора направление
  починки в drift-детекторе разделено **по типу поля**: значения контактов — shadow → Keycloak; флаги подтверждения —
  монотонны, «true побеждает», и дочиняется **отставшая сторона** (в том числе shadow, иначе детектор откатывал бы
  честную верификацию). Детали — §3a. Долг «drift-детектор» закрыт реализацией, живой приёмкой и этим правилом.
- **Обновление 15.10.2026 (вечер): B2 решён — sign-off получен, развилки закрыты:**
  (1) `verify`: **отзыв доступа ДО применения**, `503` = ничего не применено, `changeToken` жив, повтор разрешён,
  заголовок `Retry-After`; (2) повторный `verify` после успеха → **`200 UserDto` идемпотентно** (запись `applied`
  живёт до TTL токена); (3) неудачная компенсация = инцидент с алертом, трио едет **без feature-flag**, runbook в
  `DEPLOYMENT.md`, drift-детектор — долг после Auth v1; (4) `handle` — «несекретный, но непубличный», наружу не отдаём;
  (5) `test@test.com` — осознанное исключение (dev-фикстура, в прод не поедет). Итог: реализация трио разрешена.
- **Обновление 15.10.2026: B1 решён — путь B (стабильный `handle`).** Координатор выбрал: `username` становится
  неизменяемым и не связанным с контактом (`usr_<16 hex>`, генерируется при регистрации, хранится в shadow `User.handle`,
  резолвится локально через `LOGIN_HANDLE_RESOLVER`); реалм **не разблокируется** (`editUsernameAllowed=false`), контракт
  не меняется, `login_hint` = handle (телефон туда не уходит, `preferred_username` как логин не используется).
  Реализовано: `9231b0f`, `c925271`; проверки и приёмка — чек-лист, § «Политика логина — путь B».
  **Следствие для этого ADR:** шаг «переименовать логин» **исключён** — значит частичный сбой «shadow ↔ Keycloak»
  остаётся только на уровне контактов (ровно сценарий B2), и порядок «shadow-транзакция → Keycloak → пере-проверка
  в транзакции → компенсация» из §B2 сохраняется без поправок. Трио `contact-change/request|verify|cancel` стартует
  после sign-off по B2.
- **Связано:** ADR-0004 (Keycloak), ADR-0015 (CIBA, `username` = контакт), ADR-0011 (OTP-хранилище),
  ADR-0018 (отзыв токенов), чек-лист Phase 4

## Контекст

Phase 4 добавляет смену контакта (`contact-change/request|verify|cancel`; коды `ChangeTokenExpired`,
`ContactChangeAlreadyPending`, `ContactAlreadyExists`, `OtpInvalid`, `OtpExpired` — уже в реестре контракта v1.3).

Контакт живёт **в двух хранилищах** с разными ролями:

| Где | Что | Зачем |
| --- | --- | --- |
| Keycloak | `username` (у email-пользователя = email, у phone = телефон, ADR-0015), `email`, `emailVerified`, атрибуты `phoneNumber`/`phoneVerified` | вход (password grant, CIBA-`login_hint`), письма, Account Console |
| shadow-БД (`User`) | `email`, `phone` (`@unique`), `*_verified_at`, статус | источник правды для lookup, anti-enumeration, бизнес-логика |

В `User` есть инвариант: verified-контакт нельзя менять напрямую (422 `InvalidContacts`) — смена идёт санкционированным
путём через подтверждение кодами.

## Что показали живые проверки (15.10.2026, Keycloak 26.8.0)

| Проверка | Факт |
| --- | --- |
| Флаги реалма | `editUsernameAllowed=false`, `loginWithEmailAllowed=true`, `duplicateEmailsAllowed=false` |
| Админ-переименование при текущем конфиге | `400 error-user-attribute-read-only` (даже при `username.permissions.edit=['admin','user']`) |
| Переименование при `editUsernameAllowed=true` + `permissions.edit=['admin']` | **204** ✓, затем password-grant по **новому** логину → `300` ✓ (проверено и откатано) |
| Логин по email, когда `username` — не email | password-grant по email → `300` ✓ (KC резолвит по атрибуту `email`) |
| Коллизия email при создании | `409 User exists with same email` ✓ (KC проверяет) |
| Коллизия телефона (атрибут) | `201` ✓ — **KC уникальность телефона не проверяет**, её держит наша БД |
| Access-токен после `logout` | `/users/me` → `200` (жив), refresh → `401` ⇒ **B3 подтверждён фактом** |

## Решение

### 1. Политика `username` (B1)

- **Смена email переименования не требует** — проверено: и password-grant, и CIBA-резолвер (`findUserByNameOrEmail`)
  находят пользователя по атрибуту `email`.
- **Смена телефона требует нового `username`**, потому что у phone-пользователя логин = телефон (ADR-0015) —
  иначе CIBA-`login_hint` перестанет его находить.
- Два пути, **нужно решение координатора/владельца** (реализация не начинается до выбора):

  | Путь | Что нужно | Плюсы / минусы |
  | --- | --- | --- |
  | **(A) Разрешить переименование** | realm `editUsernameAllowed=true` + профиль `username.permissions.edit=['admin']` (чтобы пользователь себя не переименовывал) | проверено живьём (204 + вход по новому логину ✓); инвариант «логин = текущий контакт» сохраняется. Минус: меняется схема реалма (2 настройки) |
  | **(B) Стабильный handle** (рекомендация бэкенда) | без изменений реалма: `username` фиксируется при создании и не меняется; для CIBA и password-grant берём `username` из админ-API (в reauth уже так), а текущий контакт живёт в shadow-БД | реалм не трогаем, риск ниже. Минус: логин в Account Console выглядит устаревшим и содержит старый контакт |

- В обоих путях переименовываем/используем логин **только когда меняется контакт, равный текущему `username`**.

### 2. Поток (с TOCTOU-резервом и перевыпуском челленджа)

```
POST /users/me/contact-change/request    protected + X-Reauth-Token
  → проверка занятости нового контакта (409 ContactAlreadyExists)
  → один активный change на пользователя, иначе 409 ContactChangeAlreadyPending
  → РЕЗЕРВ нового контакта (Redis, TTL = TTL change) — против TOCTOU
  → челленджи: new всегда (purpose='change-contact-new'), old — по правилу I2
  → 201 { changeToken, requiresOldChallenge, oldChallengeId?, newChallengeId }

POST /users/me/contact-change/verify      protected   { changeToken, oldCode?, newCode }
  → ре-чек занятости в той же транзакции, что и запись в shadow — конфликт → 409
  → проверка кодов: OTP_CHALLENGES.verify({ target, purpose, code })
    (по target+purpose, а не по id — тогда перевыпуск челленджа через /auth/otp/send не ломает change)
  → shadow-БД (транзакция) → Keycloak (username/email/attributes/emailVerified)
  → гасим сессии KC + отзываем access-токены (ADR-0018)
  → 200 UserDto

POST /users/me/contact-change/cancel      protected   { changeToken } → 204 (снимает резерв и челленджи)
```

TTL `changeToken` — **10 минут** (уравнено с `verificationToken`, ответ координатора №3); челлендж внутри одного change
можно перевыпускать, не начиная change заново.

### 3. Частичный сбой Keycloak ↔ shadow (B2)

Порядок операций в `verify` (уточнён координатором 15.10.2026 — **отзыв ДО применения**, как в `password`/`set-password`):

1. проверка старых/новых кодов: `OTP_CHALLENGES.verify` **по target+purpose**;
2. **`RevokeUserAccessUseCase`** (`reason='contact-change'`, ADR-0018) — гасим сессии KC + метка `sub`; падение → `503`,
   контакт не тронут;
3. shadow-БД (**транзакция**): **ре-чек занятости в той же транзакции** + запись нового контакта + `activateIfPending()`;
4. Keycloak: `email` / атрибут `phoneNumber` + verified-флаги, ретраи 3×;
5. уведомления на **старый и новый** контакт (best-effort).

**Почему отзыв до применения.** Иначе достижимо состояние «применено, но не отозвано», и любой `5xx` в ответе
становится неправдой для клиента. При порядке «отзыв → применение» `503` **однозначно** означает «контакт не изменён»
(после успешной компенсации); повторный `verify` прежним access-токеном до обработчика не дойдёт вовсе (`401` по
ADR-0018) — для клиента это тоже «дальше вход заново». Факт применения пользователь видит после входа (в профиле).

**Согласованная семантика (вариант B2-1 — без нового кода контракта):**

- `503` на `verify` = **ничего не применено** (компенсация удалась), `changeToken` жив, повтор разрешён;
  в ответе — заголовок **`Retry-After`**;
- операция **идемпотентна по конечному состоянию** (повторная запись того же контакта — no-op);
- неудача ретраев KC → компенсация (откат shadow, best-effort) + статус `failed` в записи change + лог-маркер
  `contact_change_failed` + **алерт** (пользователь, ключ, желаемое и фактическое значение в обеих системах);
- повторный `verify` по тому же `changeToken`: запись `applied` → **`200 UserDto`** идемпотентно (без повторного
  применения); запись живёт до TTL `changeToken`, после TTL → `422 ChangeTokenExpired`;
- `verify` отдаёт **только `UserDto`**, без токенов (подтверждено);
- **неудачная компенсация** — это уже не `503`, а инцидент с алертом (drift). Трио едет **без feature-flag**;
  короткий runbook («повторить смену либо синхронизировать сторону») — в `DEPLOYMENT.md`; **drift-детектор**
  (сверка KC ↔ shadow + самопочинка идемпотентным повтором) — следующая задача после Auth v1, долг в чек-листе.

### 3a. Drift-детектор: правило по типу поля (ред. 4, 16.10.2026)

Детектор реализован (`ContactDriftDetectorService`, чек-лист § «Phase 4»), и на ревью координатора выяснилось, что
**починка флагов в направлении shadow → Keycloak неверна**:

1. `emailVerified = true` ставит **сам Keycloak** — когда пользователь кликает ссылку `VERIFY_EMAIL`;
2. shadow узнаёт об этом **асинхронно** (`KeycloakEventListenerService`, поллинг Admin Events);
3. значит есть окно, где `KC=true`, а `shadow=false`; попав в него, детектор **снял бы** флаг в Keycloak —
   то есть откатил честную верификацию;
4. если событие потерялось, shadow остался бы `false` **навсегда**, и детектор откатывал бы верификацию постоянно
   (ровно тот случай, ради которого он заводился, — только против пользователя).

**Правило (в одну строку: «значения — всегда из shadow; флаги — объединение, кроме случая смены значения»):**

| Поле | Правило починки |
| --- | --- |
| `email`, `phone` (значения) | **shadow → Keycloak** — значения пишет наш flow, уникальность держим мы |
| `emailVerified`, `phoneVerified` (флаги) | **флаг монотонен, «true побеждает»**: при совпавших значениях флаг = `KC \|\| shadow`, и дочиняется **отставшая сторона** (`KC=true/shadow=false` → правится **shadow**); при **разошедшихся** значениях в Keycloak пишутся значение и флаг из shadow (смена контакта легитимно сбрасывает подтверждение) |

Следствия в коде: `USER_CONTACTS.markVerified({ keycloakId, channel })` (путь тот же, что у `OnEmailVerifiedHandler`:
доменные `verifyEmail()` / `verifyPhone()` + публикация событий), лог-маркер **`contact_drift_flag_forwarded`**
(флаг дочинен в shadow; отдельно от `_healed`, чтобы такие случаи были видны), тест «Keycloak впереди по
`emailVerified`». Дополнительно: `PUT /users/{id}` — полная замена, поэтому в Keycloak пишутся **только
разошедшиеся каналы**, остальное адаптер переносит сам (read-modify-write).

**Эксплуатация:** ручная правка контакта в Account Console будет откатана детектором — предупреждение в
`DEPLOYMENT.md` §7 п.13; на проде первый прогон — с `CONTACT_DRIFT_HEAL_ENABLED=false` (сначала объём дрейфа).

### 4. Сессии и access-токены (B3)

После успешной смены доступа не должно остаться — но **только одна неделимая операция** это гарантирует:
`RevokeUserAccessUseCase` (ADR-0018) = гасим сессии KC (`POST /users/{id}/logout`, ретраи 3×) **и** ставим метку
`auth:sub-revoked:<sub>`; падение любого шага → вся операция `503`, метка не выставляется. Порядок «KC → метка»
(сначала то, что нельзя обойти refresh'ем).

Вызывается **до коммита** смены (структурная гарантия: «контакт изменён, доступ не отозван» недостижимо) с
`reason: 'contact-change'`. Для смены пароля/`set-password` — тот же юзкейс с `reason: 'password-change'`;
для `sign-out` — **не** вызывается (остаётся пер-токенный блоклист, иначе выход на одном устройстве убивал бы все).

### 5. `changeToken`

TTL 10 минут, Redis, хранится **хешем**, привязан к `keycloakId`, **не одноразовый** (нужен `verify` и `cancel`),
один активный change на пользователя.

### 6. Уведомления и подтверждения

- **I2 (кому уходит oldChallenge):** на **заменяемый** контакт, если он verified; иначе — на другой verified контакт;
  если verified-контактов нет — `requiresOldChallenge=false`.
- **I1 (уведомления):** после успешной смены уведомляем **и старый, и новый** контакт (SMS/email) — дешёвый контроль
  против незаметного угона. Подтверждение старого контакта при смене **email обязательно** (ответ координатора №2):
  иначе украденный пароль превращается в постоянный захват аккаунта.

### 7. Детали, зафиксированные на ревью

- **I6:** после смены вызываем только `activateIfPending()` — suspended не «оживает» молча.
- **I7:** нормализация до проверки уникальности (email → lowercase, телефон → E.164); контакты в логи не пишем (**PII**).
- **I8:** лимиты per-target (ADR-0011) **+ лимит на пользователя** — код/деньги уходят на новый, потенциально чужой контакт.
- **I9:** после `verify` пользователь разлогинен (логин изменился) — обязанность фронта уже передана координатором.
- **I4 (тупик для passwordless):** начать change такой пользователь не может (нужен `X-Reauth-Token`, пароля нет),
  а `set-password` требует OTP на **утраченный** контакт ⇒ тупик. Нужен админский путь восстановления **с аудитом** и
  запись в инструкцию поддержки — отдельная задача, 0017 не блокирует.
  **Решение владельца 16.10.2026: отложено целиком** — кейса в поддержке ещё не было, режим работы dev-only, Auth v1
  эта дыра не блокирует. Когда появится реальный пользователь: либо runbook через Keycloak Admin Console (с включённым
  `adminEventsEnabled` — сейчас в реалме он **выключен**, поэтому «путь через консоль» без этого не является аудитом)
  + наш структурный лог, либо админский эндпоинт по образцу `RevokeUserAccessUseCase` (отзыв доступа + аудит + ADR).

## Новые shared-порты (никаких импортов «модуль → модуль»)

- **`OTP_CHALLENGES`** (владелец — OTP-контекст): `start({ target, purpose }) → { challengeId, expiresAt }` и
  `verify({ target, purpose, code })` — проверка **по target+purpose**, чтобы перевыпуск челленджа не ломал начатый change.
- **`USER_CONTACTS`** (владелец — user-контекст): `applyVerifiedChange({ keycloakId, email?, phone? }) → UserDto`;
  внутри — новый доменный метод `User.applyVerifiedContactChange(...)`, а прямой `updateContacts` по-прежнему запрещает
  менять verified-контакт.

## Последствия

- Появляются 2 shared-порта и доменный метод; коды `ChangeTokenExpired` / `ContactChangeAlreadyPending` начинают уходить
  на провод (гардрейл обновится осознанно).
- Зависимость от **ADR-0018**: без отзыва access-токенов смена контакта не закрывает окно уязвимости.
- Нужен **drift-детектор** KC ↔ shadow (отдельная задача) — **реализован**: `ContactDriftDetectorService`
  (сверка по таймеру, keyset-пагинация, report-only режим, `identity_missing` вручную) + правило по типу поля
  в §3a (ред. 4).
- Путь (A) — две настройки реалма в DEPLOYMENT; путь (B) — правки только в коде.

## Альтернативы

| Вариант | Почему нет |
| --- | --- |
| Контакт только в shadow-БД | password-grant и CIBA-`login_hint` работают по `username` в KC → пользователя не найдут |
| Синтетический `username` (uuid) | Ломает ADR-0015: `login_hint` резолвится только по username/email |
| Менять только Keycloak | Наш lookup/anti-enumeration и уникальность контакта живут в shadow-БД |
| Интроспекция каждого access-токена в KC | Сетевой вызов на каждый запрос (отклонено в ADR-0018) |

## Ответы координатора на открытые вопросы

1. **Смена `username`** — проверить живым стеком (проверено, см. выше); переименовывать только при необходимости;
   выбор пути (A)/(B) — за координатором.
2. **Подтверждать старый контакт при смене email** — **обязательно**.
3. **TTL `changeToken`** — **10 минут** + возможность перевыпуска челленджа внутри одного change.
