# ADR 0011: OTP-челленджи — хранение в Redis, хеш argon2id, лимиты

- **Дата:** 2026-10-08
- **Статус:** Accepted

## Контекст

Phase 0 auth-suite требует OTP-сервис, от которого зависят phone-регистрация, phone-вход,
verify-contact и весь Phase 4. Контракт (`docs/auth-v1-contract.md`, v1.0) фиксирует наблюдаемое
поведение: 6 цифр, TTL 5 минут, ≤5 неверных попыток → `OtpTooManyAttempts`, лимиты отправки
(`OtpRateLimited` + `details.retryAfter`), anti-enumeration для `purpose='sign-in'`, 409
`ContactAlreadyExists` для `purpose='sign-up'`. Модель верификации (6-значный код, не magic link;
хеш argon2id; TTL) зафиксирована в ADR-0011 фронтового репозитория.

Свобода реализации (по контракту): внутреннее устройство — Redis-ключи, argon2id, структура
модулей. Нужно было выбрать: где хранить челлендж, как хешировать, где считать лимиты и как
получить проверку занятости телефона, не нарушив правило «никаких импортов между модулями».

## Решение

1. **Хранение — Redis** (уже есть в стеке как кеш/blacklist). Ключи:
   - `otp:challenge:<id>` → снапшот челленджа (JSON), TTL = **остаток** от `expiresAt`
     (повторное сохранение после неудачной попытки **не продлевает** жизнь кода);
   - `otp:active:<sha256(target|purpose)>` → id активного челленджа: при resend прошлый
     инвалидируется (гонка «два активных кода на один номер» исключена);
   - `otp:verification:<token>` → `{ target, purpose }`, TTL 10 минут, чтение через `GETDEL`
     (одноразовость);
   - target в ключах **хешируется** — PII не попадает в ключи, дампы и логи.
2. **Хеш кода — argon2id** через `@node-rs/argon2` (prebuilt N-API: win-x64 + linux-x64-gnu,
   в `node:24-bookworm-slim` не нужен build-toolchain), параметры OWASP — m=19 MiB, t=2, p=1.
   Plaintext-код не хранится и не логируется нигде, кроме dev-SMS-реализации (по чек-листу).
3. **Лимиты — счётчики в Redis**: cooldown 60 c (`SET NX EX`), 3/час на target, 10/час на IP
   (`INCR` + `EXPIRE`). Cooldown «сгорает» даже если сработал более общий лимит — осознанно:
   так повторные попытки не долбят хранилище чаще раза в минуту.
4. **Anti-enumeration** (требование контракта): для `purpose='sign-in'` челлендж создаётся
   **всегда** (одинаковый ответ и одинаковая работа), но SMS не отправляется, если номера нет.
   Для `purpose='sign-up'` занятый контакт — явная 409: UX важнее скрытности (зафиксировано
   в контракте как сознательное исключение).
5. **Занятость телефона** — shared-порт `CONTACT_LOOKUP` (`shared/application/`) + реализация
   в user-контексте, который владеет таблицей. `UserModule` помечен `@Global` и экспортирует
   **ровно этот один токен**: OTP-модуль зависит от порта, а не от модуля (импорт «модуль → модуль»
   под запретом).
6. **`DomainError.details`** — база для `details` в теле ответа (контракт требует
   `OtpRateLimited.retryAfter`; тот же механизм понадобится `PasswordPolicyViolation`).

## Последствия

Положительные:

- Redis — источник истины для короткоживущего состояния: TTL и one-shot семантика бесплатно,
  Postgres не растёт от OTP-мусора;
- argon2id без нативного toolchain: сборка образа и дев на Windows работают «из коробки»;
- челлендж недоступен без Redis — но Redis и так критичен для blacklist токенов;
- проверка занятости номера не порождает связки модулей: только shared-порт.

Отрицательные и mitigation:

- **~19 MiB и десятки миллисекунд на один хеш.** Mitigation: ≤5 проверок на челлендж, коды
  короткоживущие; при росте нагрузки параметры вынести в конфиг (сейчас константы в адаптере).
- **Потеря Redis = потеря челленджей и счётчиков** (пользователь запросит код заново,
  лимиты сбросятся). Mitigation: осознанный компромисс пилота; при недоступности Redis
  эндпоинты отдают 5xx — отдельный 503 не входит в контракт v1.0.
- **Счётчики лимитов живут в том же Redis**, что кеш: при кластеризации потребуется общий
  Redis или вынос лимитов в отдельное хранилище.
- **`@Global` на UserModule** — небольшой архитектурный компромисс ради явного порта;
  экспортируется только `CONTACT_LOOKUP`, что зафиксировано комментарием в модуле.

## Альтернативы

- **HMAC-SHA256 вместо argon2id** — быстрее и дешевле по памяти, но чек-лист и ADR-0011
  требуют именно argon2id (сопротивление offline-перебору при утечке дампа Redis).
- **Plaintext-код в Redis** — отвергнуто чек-листом («не хранить plaintext»).
- **verificationToken как JWT** — не отозвать до истечения, нужен ключ и валидация;
  Redis one-shot (`GETDEL`) проще и строже по семантике «одноразовый».
- **Челленджи в Postgres** — переживают рестарт, но требуют фоновой очистки и дают
  больше I/O на hot-path ввода кода.
- **Лимиты in-memory** — не работают при нескольких инстансах приложения.
- **Импорт user-модуля в OTP** — нарушает правило границ модулей; выбран shared-порт.
