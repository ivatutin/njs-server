# ADR 0014: Верификация телефона — два канала (SMS-код и обратный звонок)

- **Дата:** 2026-10-14
- **Статус:** Accepted

## Контекст

Phase 2 (phone-регистрация и вход) требует доказать владение номером. Сейчас это делает Phase 0:
`POST /auth/otp/send` → SMS-код → `POST /auth/otp/verify` → короткоживущий одноразовый
`verificationToken`, который предъявляется в sign-up/sign-in (ADR-0011).

Бизнес-требование изменилось: **основной канал подтверждения — обратный звонок**, SMS-код остаётся
вторым каналом. Провайдер — SMS.ru, метод callcheck (`sms.ru/api/call`):

1. `POST https://sms.ru/callcheck/add` (`api_id`, `phone`, `ip` пользователя, `json=1`) → `check_id`,
   `call_phone` / `call_phone_pretty` — номер, на который должен позвонить пользователь;
2. пользователь звонит; провайдер сбрасывает звонок (для звонящего бесплатно) и **сам** уведомляет нас
   вебхуком; окно на звонок — **5 минут**;
3. `POST https://sms.ru/callcheck/status` (`api_id`, `check_id`) → `check_status`: **400** — звонка не
   было, **401** — номер подтверждён, **402** — время истекло либо неверный `check_id`.

Ограничения и риски провайдера, которые определяют решение:

- звонок принимается на **общий сервисный номер**, привязка — **по номеру звонящего** (DTMF-кода нет);
- значит, на номер может быть только **одна активная заявка** и подтверждение невозможно, если у
  пользователя **скрыт определитель номера** (CLIR) либо он звонит с другого телефона;
- **вебхук не документирован как подписанный** и формат его тела публично не описан (только
  «отправляем HTTP-оповещение, что авторизация пройдена» + «вы также можете запрашивать состояние
  самостоятельно через API»), регистрация URL — `POST https://sms.ru/callback/add`, URL обязан быть `https://`;
- проверка идёт по `ip` пользователя (не сервера), есть настраиваемый лимит звонков (ошибка `508`).

Ограничения нашего проекта: правило «никаких импортов между модулями» (только shared-порты), запрет на
изменение уже замороженных эндпоинтов/DTO контракта и требование «изменение канала верификации не должно
менять архитектуру в целом».

## Решение

1. **Один челлендж-стор на два канала.** Снапшот челленджа (ADR-0011) расширяется полями
   `method: 'otp' | 'call'`, `providerCheckId?`, `callTo?`. Ключ `otp:active:<sha256(target|purpose)>`
   сохраняется: новый старт вытесняет предыдущий челлендж — это обязательно, т.к. привязка звонка идёт
   по номеру. Добавляется обратный индекс `otp:call:<check_id>` → `challengeId` (TTL = окно звонка),
   чтобы вебхук находил нашу заявку.
2. **Новый порт домена OTP-модуля** `PHONE_CALL_PROVIDER`:
   `start({ phone, userIp }) → { providerCheckId, callTo } | null`, `status(providerCheckId) →
   'pending' | 'verified' | 'expired' | 'failed'`. Реализация — `SmsRuCallcheckProvider`
   (инфраструктурный адаптер, `api_id` из env, POST на `sms.ru/callcheck/{add,status}`; `userIp` берём
   существующим `resolveClientIp(request)`). Фиче-флаг `SMSRU_CALLCHECK_ENABLED`: в dev/CI выключен,
   подставляется фейк.
3. **`verificationToken` остаётся единственной точкой истины** и выдаётся из того же
   `VERIFICATION_TOKEN_ISSUER` (`{ target, purpose }`, TTL 10 минут, `GETDEL`). Источника выдачи теперь
   два: успешный `POST /auth/otp/verify` и подтверждение звонка. Поэтому `POST /auth/sign-up/phone` и
   `POST /auth/sign-in/phone` **не меняются** — они по-прежнему принимают `verificationToken`.
4. **Вебхук — триггер, а не источник истины.** Тело вебхука не считается доверенным (подпись не
   документирована). Хендлер: извлекает `check_id` → вызывает `callcheck/status` с нашим `api_id` →
   при `401` **атомарно** (`SET NX`) переводит челлендж в `verified` и выдаёт `verificationToken`;
   отвечает быстро 2xx, всё логирует. Дополнительно: allowlist по IP провайдера (список уточняется у
   SMS.ru), корреляция строго по `check_id` нашей заявки.
5. **Fallback без вебхука.** Эндпоинт ожидания для фронта (`GET /auth/phone/call/:challengeId`) сам
   опрашивает `callcheck/status` с троттлингом (не чаще, чем раз в 5 с на челлендж). Это делает систему
   работоспособной в dev/CI и при потере вебхука; публичный `https`-эндпоинт нужен только для
   мгновенного уведомления.
6. **SMS-код остаётся вторым каналом** (и fallback для CLIR, недоступности провайдера и по желанию
   пользователя). В ответе `POST /auth/phone/call` это явно помечено флагом `otpFallback: true`.
7. **Anti-enumeration сохраняется:** при `purpose='sign-in'` заявка создаётся всегда (в т.ч. для
   незарегистрированного номера), ответ идентичен; `409 ContactAlreadyExists` для `purpose='sign-up'`
   остаётся осознанным исключением (как в Phase 0).
8. **Маппинг состояний провайдера в наш домен:** `400 → 'pending'`, `401 → 'verified'`, `402 → 'expired'`,
   request-level `202 → 'failed'`, `508 → OtpRateLimited` + `details.retryAfter`, `301/302` → ошибка
   конфигурации (5xx, алерт). `expired` / `failed` — это **значения поля `status`** ответа `GET`, а не коды
   реестра: контракт v1.2 новых кодов не вводит (терминальное состояние — нормальный исход поллинга,
   а не ошибка клиента). Провайдерский `401` — это **«номер подтверждён»**, а не «не авторизован»:
   фиксируем тестом, чтобы не перепутать с HTTP-семантикой.
9. **Кросс-канальное вытеснение** (рекомендация координатора, принята). Активный челлендж на
   `(phone, purpose)` — **один на оба канала**: ключ `otp:active:<sha256(target|purpose)>` общий, поэтому
   `POST /auth/otp/send` вытесняет активный звонковый челлендж, а `POST /auth/phone/call` — активный
   OTP-челлендж. Вытесненный челлендж отвечает `200 { status: 'expired' }`; следствие для фронта — после
   запроса кода поллинг звонка прекращается (и наоборот).
10. **`GET` идемпотентен.** Выданный `verificationToken` сохраняется в снапшоте челленджа, поэтому
    повторный `GET` возвращает **тот же** токен; одноразовость обеспечивает отдельный ключ
    `otp:verification:<token>` (`GETDEL`, TTL 10 минут). Неизвестный `challengeId` → `200 { status:
    'expired' }` (не 404 и не 422).

**Вне скоупа этого ADR:** каким именно способом бэкенд получает **Keycloak-токены** пользователя после
подтверждения (Token Exchange / JWT Authorization Grant / технический пароль) — это отдельное решение и
отдельный ADR. Верификация телефона от него не зависит: оба канала выдают `verificationToken`, а минт
токенов остаётся в `sign-up/phone` / `sign-in/phone`.

## Последствия

Положительные:

- подтверждение владения номером становится «физическим»: пользователь доказывает владение SIM звонком,
  перехват SMS-кода (SIM-swap, переадресация) перестаёт быть единственным сценарием атаки;
- архитектура не меняется: тот же challenge-стор, тот же `verificationToken`, те же эндпоинты Phase 2 —
  меняется только источник события «подтверждено»;
- вебхук не является доверенным входом: даже без подписи подделать подтверждение нельзя, потому что
  истину мы спрашиваем у провайдера авторизованным запросом;
- решение переживает недоставку вебхука (polling-fallback) и работает в dev без публичного адреса.

Отрицательные и mitigation:

- **Два канала = две ветки состояния и вдвое больше тестов.** Mitigation: общий челлендж-стор и один
  issuing-point `verificationToken`; тесты — по одному suite на канал + тесты на общий инвариант
  «токен одноразовый и привязан к `{target, purpose}`».
- **Верификация недоступна при CLIR / звонке с другого номера.** Mitigation: обязательный UI-путь
  «получить код вместо звонка», флаг `otpFallback` в ответе.
- **Зависимость от внешнего сервиса (SMS.ru) на критичном пути входа.** Mitigation: OTP-канал как
  fallback, фиче-флаг `SMSRU_CALLCHECK_ENABLED` (можно «погасить» call-канал без релиза логики),
  обработка 5xx провайдера без утечки деталей.
- **Ответственность за заявки у провайдера (утечка `check_id`?).** `check_id` не является секретом и
  бесполезен без нашего `api_id`; в логи не пишем `api_id`.
- **Публичный вебхук-эндпоинт** — новая внешняя поверхность. Mitigation: тело не используется как
  истина, allowlist IP провайдера, корреляция по нашему `check_id`, идемпотентность (`SET NX`),
  отдельный rate-limit и лог всех входящих вызовов.
- **Асинхронность усложняет UX** (экран ожидания, таймер 5 мин). Mitigation: polling 3–5 с + терминальные
  состояния как поле `status` в ответе `GET` (`expired` / `failed`), а не коды ошибок.
- **Скрытая стоимость**: платим за старт заявки, в т.ч. для незарегистрированных номеров (anti-enum).
  Mitigation: собственные лимиты + настройка лимитов в ЛК провайдера (ошибка `508`).

## Альтернативы

- **Минтить токены прямо в вебхуке** (и держать их в Redis до запроса фронта). Отвергнуто: удлиняет
  критичный путь (минт в процессе обработки вебхука), требует хранить токены (TTL, шифрование,
  идемпотентность повторов), и связывает механизм верификации с механизмом минта. Вариант «вебхук только
  фиксирует `verified`» оставляет минт там, где он уже был.
- **Доверять телу вебхука.** Отвергнуто: подпись не документирована, формат тела не описан.
- **Только polling без вебхука.** Проще (нет публичного эндпоинта), но даёт задержку до нескольких секунд
  и лишние вызовы `callcheck/status`; оставлено как fallback, а не как основной путь.
- **Только OTP, без звонков.** Отвергнуто: противоречит бизнес-требованию (звонок — основной канал).
- **Другой провайдер** (Twilio, Voximplant, собственный DID + приём звонков). Отвергнуто на этом этапе:
  SMS.ru уже выбран бизнесом, даёт сервисный номер, вебхук и бесплатный для звонящего звонок.
- **DTMF-модель** (общий номер + код, вводимый в тональном режиме). Провайдер её не предлагает:
  привязка идёт по A-номеру, кода нет.
- **Состояние заявок в Postgres** вместо Redis. Отвергнуто: заявка живёт 5 минут, нужна горячая проверка
  с TTL и one-shot семантикой — это профиль Redis (ADR-0011).

## Что проверить перед реализацией (spike)

1. Активировать callcheck в ЛК SMS.ru, получить `api_id`; прогнать `callcheck/add` и `callcheck/status`
   руками на dev-номере (проверить `check_status` 400 → 401, окно 5 минут).
2. Уточнить у SMS.ru: точный формат тела вебхука для callcheck и наличие подписи; список IP отправителя;
   цену и лимиты (настройка `508`); поведение при скрытом номере; возможность отмены заявки; несколько
   заявок на один номер.
3. Зарегистрировать `callback/add` (нужен публичный `https`); в dev проверить polling-fallback без вебхука.
4. Решить судьбу `KC_FEATURES=token-exchange,impersonation` в `docker/keycloak/Dockerfile` (незакоммиченное
   изменение) — к этому ADR не относится, решается вместе с выбором механизма выдачи Keycloak-токенов.
