# ADR 0020: Авторизация — realm-роли → claims → `@Roles`

- **Дата:** 2026-10-15
- **Статус:** **Accepted** (решение координатора). Реализовано: `@Roles('admin')` на админских методах,
  денлист встроенных ролей, разовая чистка shadow-БД.
- **Связано:** ADR-0004 (Keycloak как IdP), ADR-0018 (отзыв доступа), `docs/auth-suite-backend-checklist.md`

## Контекст

Машинерия авторизации в проекте уже была: `JwtAuthGuard` и `RolesGuard` подключены глобальными `APP_GUARD`
(порядок «JWT → роли»), есть `@Roles()` / `ROLES_KEY`, роли берутся из `realm_access.roles`, у токена проверяется
`azp`. Но `@Roles` **нигде не применялся**: админские операции `UserController` (`POST /users`, `GET /users/:id`,
`PATCH /users/:id/profile|contacts`, `POST /users/:id/email|phone/verify`, `POST /users/:id/suspend|activate`,
`DELETE /users/:id`) мог дёрнуть **любой** аутентифицированный пользователь.

## Решение

1. **MVP-роль — только `admin`.** `manager` зарезервирован. Вектор продукта: ролей будет много (редакторы контента,
   цензоры, рекламодатели, подписчики), поэтому добавление роли обязано быть **операцией реалма**, без правок кода.
2. **Выдача роли — вручную через Keycloak Admin Console** (шаг в `DEPLOYMENT.md §7`). Свой эндпоинт `role.manage`
   не делаем.
3. **`@Roles('admin')` — по методам, не на классе.** `GET /users/me` живёт на том же контроллере, поэтому класс-левел
   сломал бы профиль обычным пользователям. Закрыты ровно 9 админских методов; без ролей — `GET /users/me`
   и весь `AccountSecurityController` (`set-password`, `password`).
4. **`AdminUsersController` с класс-левелом (default-deny) — не в этой правке**: он меняет пути, которые уже дёргает
   фронт; отдельным рефакторингом позже.
5. **Встроенные роли — денлист, а не allowlist** (`offline_access`, `uma_authorization`, `default-roles-<realm>`,
   константы в `src/modules/auth/infrastructure/keycloak/realm-roles.ts`), применяется в
   `KeycloakAdapter.verifyAccessToken` → в claims, `User.roles` и DTO встроенные роли не попадают. Разовая чистка
   уже сохранённых значений — миграция `20261015170000_clean_builtin_roles` (тот же денлист, при правке списка
   обновлять оба места).
6. **Жизненный цикл роли — обязательно знать:**
   - после выдачи роли нужен **новый токен** (вход или refresh): роль берётся из JWT;
   - снятие роли действует только **после истечения access-токена** (300 с); если нужно немедленно — вызывать уже
     реализованный `RevokeUserAccessUseCase` (ADR-0018) и уводить пользователя на повторный вход.

## Направление на будущее (не строим сейчас)

«Много ролей → права»: `@RequirePermission` + маппинг роль→права, чтобы контроллеры не распухали от списков ролей
и чтобы одну и ту же возможность можно было дать разным ролям без правок кода. Зафиксировано как направление:
текущая модель — роли, переход к правам — отдельная задача.

## Последствия

- Тесты: `test/interfaces/roles.guard.spec.ts` (5 кейсов), `test/infrastructure/realm-roles.spec.ts` (4),
  `test/interfaces/user.controller.roles.spec.ts` (4: админские методы требуют `admin`, `me` — без ролей,
  класс-левела нет, `AccountSecurityController` без ролей).
- Прод-шаг: создать realm-роль `admin`, назначить оператору, проверить `realm_access.roles` в токене.
- Долг из чек-листа («у `UserController` нет RBAC») снят.
- Открытым остаётся brute-force/лимиты на `/auth/reauth` (в эту правку не входило).
