# ADR 0018: Отзыв access-токенов (logout, смена контакта, смена пароля)

- **Дата:** 2026-10-15
- **Статус:** **Proposed** — нужно решение по механизму (у бэкенда есть рекомендация); заводится по требованию
  ревью ADR-0017 (блокер B3).
- **Связано:** ADR-0017 (смена контакта), ADR-0004 (Keycloak как IdP), существующий `TOKEN_STORE` (блоклист access-токенов)

## Контекст

`JwtAuthGuard` валидирует **stateless** JWT по JWKS и проверяет лишь блоклист *конкретного* токена (наш `sign-out`).
Keycloak при `logout` убивает сессии и refresh-токены, но **уже выданный access-токен продолжает работать до `exp`**.

Подтверждено живым стеком 15.10.2026 (Keycloak 26.8.0, access-token TTL 300 с):

```
sign-in/phone → access token
POST /admin/realms/app/users/{id}/logout  → 204
GET /users/me с ТЕМ ЖЕ access-токеном      → 200 (токен жив!)
POST /auth/refresh с тем же refresh-токеном → 401 (сессия убита)
```

Значит все сценарии «доступ должен умереть немедленно» — sign-out, смена контакта (ADR-0017), смена пароля
(`/users/me/password`, `set-password`), админский logout — сейчас закрываются только на уровне refresh-токенов.
Окно уязвимости = TTL access-токена (300 с), а при смене контакта этого мало: логин уже другой, а старый токен ещё живой.

## Варианты

| Вариант | Как работает | Оценка |
| --- | --- | --- |
| **(A) `sessions_valid_from` в shadow-User** + проверка `iat` в guard | в БД появляется метка «доступ действителен с…», guard сравнивает `iat` | требует чтения локального пользователя на **каждый** запрос (лишний DB-хоп в guard) + миграция |
| **(B) Метка отзыва по `sub` в Redis** (рекомендация) | `auth:sub-revoked:<sub> = timestamp`, TTL = TTL access-токена + запас; guard сравнивает `iat < revokedAt` → 401 | один Redis-`GET` — **ровно тот, что уже делается** для блоклиста токена; без миграций; отзывает все сессии пользователя сразу |
| (C) Интроспекция токена в Keycloak на каждом запросе | вызов KC на запрос | сетевой хоп и зависимость от KC на каждом запросе — отклонено |

## Решение (рекомендация бэкенда)

Вариант **(B)**:

1. Расширяем существующий порт `TOKEN_STORE` (новый порт не нужен):
   - `revokeUserTokens(sub: string, ttlSeconds: number): Promise<void>` — ставит метку отзыва;
   - `isUserRevoked(params: { sub: string; issuedAt: number }): Promise<boolean>` — сравнивает `iat` с меткой.
2. `ValidateTokenUseCase` (его вызывает `JwtAuthGuard`) проверяет обе вещи: блоклист конкретного токена (как сейчас) и
   метку отзыва по `sub`. Для этого `TokenClaims` получает поле **`issuedAt`** (из `iat` payload'а).
3. Метку ставит каждый сценарий, где доступ должен умереть:
   - `sign-out` — остаётся блоклист конкретного токена **+** метка по `sub` (одним вызовом дешевле, чем кажется);
   - `contact-change/verify` — после успешной смены (ADR-0017);
   - `password` / `set-password` — после смены пароля;
   - админские операции (suspend/delete — вне auth-suite) — по тому же порту.
4. TTL метки = **TTL access-токена + запас** (`600` с при текущих 300 с): после её истечения все токены, выданные до
   отзыва, уже просрочены сами — метка больше не нужна.

## Последствия

- В `TokenClaims` появляется `issuedAt` (правки в адаптере IdP + тесты claims).
- Redis-нагрузка не меняется: guard уже делает один `GET` (блоклист), станет два `GET` — можно объединить в один
  pipeline/MGET, если понадобится.
- Logout и смена пароля начинают немедленно обрывать доступ, а не через TTL.
- Наблюдаемость: лог `token revoked by sub` на уровне debug, без PII.

## Открытые вопросы

1. Нужно ли отзывать по `sub` при обычном `sign-out` (сейчас блоклиста конкретного токена достаточно для клиента) —
   рекомендация: **да**, чтобы не оставлять живых access-токенов при выходе.
2. Подтвердить TTL access-токена в проде (в dev `expires_in: 300`) — от него берётся TTL метки.
