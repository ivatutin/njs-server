# ADR 0018: Отзыв доступа — один неделимый юзкейс (KC-сессии + метка по `sub`)

- **Дата:** 2026-10-15
- **Статус:** **Accepted** (решение координатора 15.10.2026, `docs/handoff/njs-server-reply-adr-0018.md`) и
  **реализован** (см. раздел «Живой acceptance»). Механизм (B) принят; в ADR внесены 4 условия ревью:
  **C1** (неделимость), **C2** (семантика `iat`), **C4** (TTL из конфига), плюс защита в глубину и список тестов.
- **Связано:** ADR-0017 (смена контакта — потребитель №1), ADR-0004 (Keycloak), ADR-0011 (потеря Redis = сброс состояния)

## Контекст

`JwtAuthGuard` валидирует **stateless** JWT по JWKS и знает только блоклист *конкретного* токена (наш `sign-out`).
Keycloak при `logout` убивает сессии и refresh-токены, но **уже выданный access-токен живёт до `exp`**.

Подтверждено живым стеком 15.10.2026 (Keycloak 26.8.0, `expires_in: 300`):

```
sign-in/phone → access token
POST /admin/realms/app/users/{id}/logout  → 204
GET /users/me с ТЕМ ЖЕ access-токеном      → 200 (токен жив!)
POST /auth/refresh с тем же refresh-токеном → 401 (сессия убита)
```

## Решение: отзыв — **одна неделимая операция**

Проблема не в метке по `sub`, а в том, что отзыв состоит из **двух** действий, и по отдельности ни одно не защищает:

1. убить сессии/refresh-токены в Keycloak — иначе `POST /auth/refresh` выдаст **новый** токен с `iat > revokedAt` и метку обойдёт;
2. поставить метку «токены, выданные до X, мертвы» — иначе старый access-токен живёт до `exp`.

Поэтому появляется **единственная точка входа**:

```
auth/application/use-cases/revoke-user-access.use-case.ts

command: { keycloakId /* = sub */, reason: 'contact-change' | 'password-change'
            | 'admin-suspend' | 'admin-delete' | 'logout-everywhere' }

execute():
  1) Keycloak: logoutAllSessions(keycloakId)      // POST /admin/realms/{realm}/users/{id}/logout, ретраи 3×
  2) Redis:    revokeUserTokens(keycloakId, ttl)  // auth:sub-revoked:<sub> = floor(now / 1000)
```

**Порядок принципиален:** сначала то, что **нельзя обойти**. Упал шаг 1 → отзыва нет (и метка не ставится, иначе клиент
обойдёт её refresh'ем); упал шаг 2 → refresh уже мёртв, окно ограничено TTL access-токена.

**Ошибки:** шаг 1 **не best-effort**. Половина отзыва — ложное чувство защиты, поэтому при падении (или недоступности Redis)
вся операция отдаёт **503** и метка не выставляется. Честная ошибка лучше тихого полу-отзыва.

### Где вызывается (матрица)

| Сценарий | Инициатор | Момент | Вызов |
| --- | --- | --- | --- |
| смена контакта (ADR-0017) | сам пользователь | **до** коммита смены | `reason: 'contact-change'` |
| смена / установка пароля | сам пользователь | **до** коммита | `reason: 'password-change'` |
| admin suspend / delete | админ | до применения | `'admin-suspend'` / `'admin-delete'` |
| **`sign-out`** | сам пользователь | — | **отзыв по `sub` НЕ вызывается**, остаётся пер-токенный блоклист |
| «выйти везде» (если появится) | пользователь | — | тот же юзкейс, `'logout-everywhere'` |

**Почему `sign-out` исключён:** отзыв по `sub` при выходе = «выход на одном устройстве = выход везде». Это меняет продукт
и противоречит принятому решению: «выйти на всех устройствах» — отдельная функция через Keycloak Account Console.

**Почему «до коммита»:** это *структурная* гарантия — состояние «контакт изменён, но доступ не отозван» становится
недостижимым по построению, а не по договорённости. Клиент при этом сразу разлогинен (`verify` → 200, следующий запрос → 401);
обязанность фронта уже передана координатором.

## C2. Семантика сравнения `iat` (зафиксировано)

- единицы — **секунды** (JWT `iat` целочисленный), значение метки = `floor(now / 1000)`;
- правило — **строгое** `iat < revokedAt` → `401`; окно ≤ 1 с: токен, выданный в **секунду** отзыва, остаётся живым
  (это и есть свежий вход после отзыва). Альтернатива `iat <= revokedAt` закрывает и его, но убивает повторный логин
  в ту же секунду — **не выбираем**;
- токен **без `iat`** → `401` (**fail-closed**, не «считаем валидным»);
- оба чтения — одним **`MGET`** (блоклист токена + метка) на горячем пути guard'а;
- проверка выполняется в `ValidateTokenUseCase` (его вызывает `JwtAuthGuard`), поэтому все защищённые эндпоинты
  получают её автоматически.

## C4. TTL метки — из одной конфигурации

`TTL_метки = ACCESS_TOKEN_TTL + запас`, оба значения берутся из **одной** конфигурации (`ACCESS_TOKEN_TTL_SECONDS`
и константа запаса), иначе смена TTL в проде тихо сломает отзыв. `ACCESS_TOKEN_TTL_SECONDS` обязан совпадать с
настройкой реалма Keycloak (в dev `expires_in: 300`) — проверить в проде живым стеком.

Явно фиксируем: **потеря Redis = отзывы сбрасываются** (тот же компромисс, что в ADR-0011; в compose включён AOF).

## Защита в глубину

| # | Мера | Статус |
| --- | --- | --- |
| 1 | Короткий access TTL (300 с; 120 с — лучше) | конфиг реалма; 300 с сейчас |
| 2 | Refresh-token rotation в Keycloak (`Revoke Refresh Token`) | настройка реалма — задача настройки |
| 3 | Проверять `azp` в guard: только токены нашего клиента `app-backend` (иначе пройдёт токен Account Console) | **реализуется вместе с этим ADR** |
| 4 | Уведомление пользователю о security-событии (смена контакта/пароля, отзыв сессий) | задача (нотификаций в бэкенде пока нет) |
| 5 | Метрика отказов guard по причине `sub-revoked` + алерт при падении шагов отзыва | задача (метрик-инфры пока нет, пишем в лог) |

## Тесты

- токен, выданный **до** отзыва → `401`;
- свежий токен (спустя ≥ 1 с после отзыва) → `200`;
- `refresh` после отзыва → `401`;
- токен **второго устройства** → `401`;
- шаг «KC logout упал» → операция падает `5xx`, метка **не** выставлена;
- шаг «Redis недоступен» → `5xx`;
- `sign-out` **не** отзывает по `sub` (пер-токенный блоклист как раньше).

## Чего не делать

- Не вызывать отзыв по `sub` в `sign-out`.
- Не реализовывать отзыв там, где сессии Keycloak не гасятся (обход через refresh).
- Не делать шаг 1 «best-effort»: падение = отказ операции, а не тихий полу-отзыв.
- Не менять контракт: новых эндпоинтов и кодов ADR не вводит (`503` — существующая семантика отказа инфраструктуры).

## Живой acceptance (15.10.2026, Keycloak 26.8.0 + Redis)

```
password grant → токен B (iat 1792057488) · /users/me → 200 active
пауза 2 с
POST /auth/reauth + POST /users/me/password → 204 (отзыв выполнен)
   marker auth:sub-revoked:<sub> = 1792057490 · iat=1792057488 < 1792057490 → True
/users/me с токеном B        → 401 InvalidToken «Token has been revoked»   (метка по sub работает)
/auth/refresh с токеном B    → 401 InvalidToken «Invalid refresh token»    (сессии Keycloak убиты)
свежий вход (новый пароль)   → 200 active                                  (окно ≤ 1 с не мешает)
sign-out с токеном C2        → C2 401, C1 (тот же пользователь, другое устройство) → 200 active
                               (sign-out НЕ отзывает по sub — как и требуется)
```

**Наблюдение по C2:** когда токен выдан **в ту же секунду**, что и отзыв, он остаётся живым — ровно как задумано
строгим `iat < revokedAt`. Воспроизведено живьём (первая проверка дала `iat == revokedAt` → 200), поэтому тесты
отзыва обязаны иметь разрыв ≥ 1 с между выдачей токена и отзывом.
