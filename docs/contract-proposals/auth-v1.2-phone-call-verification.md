# Предложение к контракту Auth v1.x: v1.1 → v1.2 (верификация телефона обратным звонком)

- **Класс изменения:** аддитивное (2 новых эндпоинта, **без новых кодов**) → `v1.1 → v1.2` по таблице контракта
- **Запрашивает:** backend-сессия (`njs-server`), 2026-10-14
- **Статус:** **Accepted** (2026-10-14, решение координатора) — принято с одним изменением: терминальные состояния `GET` отдаются как 200 + `status`, новые коды в реестр не вносятся. См. § «Итог рассмотрения» в конце — он отменяет пункты про 422 и про коды `CallChallenge*`
- **Ломает ли фронт:** нет. Инвариант («клиент никогда не ломается на неизвестном коде»: `matchError` → `false`, `getErrorMessage` → «Что-то пошло не так») сохраняется; новые эндпоинты фронт просто пока не вызывает

## Зачем

Основной канал подтверждения телефона по бизнес-требованию — **обратный звонок** (провайдер SMS.ru,
метод callcheck); SMS-код остаётся вторым каналом. Провайдер отдаёт номер, пользователь звонит,
провайдер детектирует звонок и уведомляет бэкенд вебхуком.

Следствие: результат подтверждения приходит **асинхронно**, поэтому схема «синхронно получили
`verificationToken` из `POST /auth/otp/verify` и сразу предъявили в sign-up/sign-in» дополняется
фазой «старт → ожидание → токен».

Что при этом **не меняется** (принципиально, см. ADR-0014):

- форма `TokenPair` и всех уже замороженных ответов;
- `verificationToken` (привязан к `{ target, purpose }`, TTL 10 минут, одноразовый) и эндпоинты
  `POST /auth/sign-up/phone`, `POST /auth/sign-in/phone` — они лишь получают **второй источник выдачи** токена;
- anti-enumeration и семантика `409 ContactAlreadyExists` для `purpose='sign-up'`.

## Что добавляется

### 1. `POST /auth/phone/call` — public

Старт звонковой верификации: создаёт челлендж и запрашивает у провайдера номер для звонка.

```ts
body: { phone /* E.164, как в otp/send */, purpose }

purpose ∈ 'sign-up' | 'sign-in' | 'verify-contact' | 'change-contact-old'
        | 'change-contact-new' | 'set-password'   // тот же enum, что у POST /auth/otp/send

200 → {
  challengeId,          // тот же тип идентификатора, что у OTP-челленджа
  channel: 'phone',
  method: 'call',       // отличает от OTP-челленджа
  callTo,               // номер, на который должен позвонить пользователь: '+7 (800) 500-8275'
  expiresAt,            // ISO; окно на звонок — 5 минут (ограничение провайдера)
  cooldownSeconds: 60,  // как в OtpChallengeResponse
  otpFallback: true     // SMS-код можно запросить тем же номером через POST /auth/otp/send
}

409 ContactAlreadyExists   // только purpose='sign-up' — как в otp/send
422 OtpRateLimited         // details: { retryAfter: number } — как в otp/send
```

Примечания:

1. `callTo` — **общий сервисный номер провайдера**, а не уникальный на заявку; привязка звонка идёт по
   номеру звонящего. Требование к UI: «звонить нужно именно с указанного номера».
2. Anti-enumeration: при `purpose='sign-in'` эндпоинт **всегда** отвечает 200 — заявка у провайдера
   создаётся и для незарегистрированного номера (иначе сам ответ выдаёт наличие аккаунта).
3. На один `(phone, purpose)` допускается **один активный челлендж**: новый старт вытесняет предыдущий
   (как resend у OTP), поэтому `GET` по вытесненному `challengeId` → `422 CallChallengeExpired`.
4. Провайдер недоступен на старте → **503** с телом `{ error, message }`; новый код в реестр намеренно
   **не вводим** (фронт покажет generic). Если координатор считает иначе — просим отдельный код
   (`CallChallengeUnavailable`) отдельным предложением.

### 2. `GET /auth/phone/call/:challengeId` — public

Ожидание результата. Фронт опрашивает эндпоинт; рекомендованный интервал — 3–5 с.

```ts
200 → { challengeId, status: 'pending' }                      // звонка ещё не было
200 → { challengeId, status: 'verified', verificationToken }   // успех: токен можно предъявлять
422 CallChallengeExpired                                      // окно истекло / челлендж неизвестен или вытеснен
422 CallChallengeFailed                                       // details: { reason } — подтверждение невозможно
```

- `verificationToken` — **ровно тот же**, что выдаёт `POST /auth/otp/verify`. Дальше фронт вызывает уже
  существующие `POST /auth/sign-up/phone` / `POST /auth/sign-in/phone` **без изменений**.
- Токен выдаётся один раз (одноразовый через `GETDEL`), в том числе если ответ на `GET` был повторён.
- Терминальные состояния отдаются кодом (422), а `pending`/`verified` — успехом: это согласовано с
  остальной семьёй кодов контракта.
- **Альтернатива по форме** (на решение координатора): отдавать `status: 'expired' | 'failed'` со 200.
  Плюс — проще polling-loop на клиенте; минус — коды не задействуются.

## Коды для реестра (аддитивно, 2 шт.) — ❌ ~~отклонено координатором~~ (см. § «Итог рассмотрения» в конце)

| Код | HTTP | Когда | `details` |
|---|---|---|---|
| `CallChallengeExpired` | 422 | окно на звонок (5 мин) истекло; челлендж неизвестен или вытеснен новым стартом | — |
| `CallChallengeFailed` | 422 | подтверждение невозможно: провайдер отклонил заявку (номер указан неверно), заявка аннулирована | `{ reason: string }` |

Имена — по правилу контракта `<Домен><Условие>`, PascalCase, без суффикса `Error`. Один код = один
HTTP-статус. Оба кода — только для звонкового канала; OTP-канал продолжает отдавать `OtpExpired` /
`OtpInvalid` / `OtpTooManyAttempts`.

## Обязанности фронта (вне этого репозитория)

- `vue-app-base/src/shared/api/error-codes.ts` — добавить `CallChallengeExpired`, `CallChallengeFailed`
  в `ErrorCode` + `ERROR_MESSAGES` (если применяется вариант с 422).
- `vue-app-base/docs/integration-backend.md` § «Auth endpoints planned» — описать 2 новых эндпоинта.
- UI: показ `callTo` (+ `tel:`-ссылка), таймер до `expiresAt` (5 минут), polling 3–5 с, кнопка
  «получить код вместо звонка» (`otpFallback`), корректный текст «звонить с этого же номера».

## Что НЕ входит в контракт (свобода реализации, как и раньше)

- вебхук провайдера (`POST /callbacks/smsru` или иной путь) — server-to-server, вне фронтового API;
- `check_id` провайдера, `check_status` (400/401/402), поля `call_phone_pretty` / `call_phone_html`;
- порт `PHONE_CALL_PROVIDER`, адаптер провайдера, флаги `SMSRU_CALLCHECK_ENABLED`, ключи Redis;
- конкретный провайдер и его тарифы.

## Риски и открытые уточнения (до реализации)

1. **Цена callcheck** не опубликована (на сайте SMS.ru — только тарифы SMS) → уточнить в ЛК/поддержке.
2. **CLIR**: при скрытом определителе номера подтверждение невозможно → обязателен UI-путь «ввести код».
3. **Лимит звонков** настраивается в ЛК (ошибка `508`) → согласовать с нашими лимитами (3/час на target,
   10/час на IP, cooldown 60 с).
4. **Формат вебхука и наличие подписи** публично не документированы → не доверяем телу, истину берём из
   `callcheck/status`; список IP провайдера — для allowlist.
5. **Публичный `https`** для вебхука: в проде — reverse proxy, в dev — опционально (работает polling-fallback).
6. Требуется ли отдельно включать услугу и настраивать её в ЛК, поддерживаются ли зарубежные номера как
   целевые, можно ли отменять заявку.

## Как применять (для координатора)

1. Сверить форму `GET`-эндпоинта (422 vs 200 для терминальных состояний) — п. «Альтернатива по форме».
2. Внести правки в `docs/auth-v1-contract.md` (4 пункта выше) и поднять версию до v1.2.
3. Выдать задачу обеим сессиям: бэкенд — реализация (ADR-0014), фронт — реестр кодов + 2 эндпоинта в
   `integration-backend.md` + UI.

## Итог рассмотрения координатором (2026-10-14)

**Принято с одним изменением.** Контракт поднят до **v1.2** (см. `docs/auth-v1-contract.md`, changelog 14.10.2026).

**Изменение (единственное):** терминальные состояния `GET /auth/phone/call/:challengeId` отдаются как
**200 + поле `status`**, а не 422. Обоснование координатора: `expired`/`failed` — нормальный исход поллинга
(окно 5 минут истекает ожидаемо), а не ошибка клиента; `GET` возвращает состояние ресурса, и 4xx для
описания состояния семантически неверен; polling-loop остаётся тривиальным и устойчивым к сети; контракт
меньше. При неизвестном `challengeId` — `200 { status: 'expired' }` (не 404 и не 422).

**Отменённые пункты этого документа:**

- раздел «Коды для реестра» — ❌ отклонён: `CallChallengeExpired` / `CallChallengeFailed` в реестр не
  вносятся, `src/shared/domain/errors/error-code.ts` не меняется;
- пункт «Обязанности фронта» про `error-codes.ts` / `ERROR_MESSAGES` — не применяется (реестр кодов не
  меняется вовсе); остаются `integration-backend.md` и UI;
- пункт «Альтернатива по форме» — принята противоположная сторона (200 + `status`);
- в changelog контракта коды не упоминаются: изменения = 2 эндпоинта + поле `status`.

**Принято без изменений:** аддитивность (`TokenPair`, `verificationToken`, замороженные эндпоинты и коды);
тело и ответ `POST /auth/phone/call`; `409 ContactAlreadyExists` (sign-up), `422 OtpRateLimited`
(`details.retryAfter`), `503` без нового кода; anti-enumeration для `purpose='sign-in'`; один активный
челлендж на `(phone, purpose)`; `cooldownSeconds: 60`; окно звонка 5 минут; «вебхук вне контракта, истина
из `callcheck/status`, телу вебхука не доверяем»; одноразовый `verificationToken` (TTL 10 минут,
привязка к `{ target, purpose }`).

**Дополнительно зафиксировано координатором:** **кросс-канальное вытеснение** — `POST /auth/otp/send` и
`POST /auth/phone/call` делят один активный челлендж на `(phone, purpose)`; после запроса кода поллинг
звонка прекращается (вытесненный челлендж отвечает `status: 'expired'`), и наоборот.

**Реализация:** ADR-0014 и `docs/auth-suite-backend-checklist.md` § Phase 2.5.
